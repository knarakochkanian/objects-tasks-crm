# Архитектура

CRM состоит из браузерного приложения на React и TypeScript, Supabase Auth и PostgreSQL. Vite собирает статические файлы для хостинга; отдельный прикладной сервер не требуется. Интерфейс, сообщения об ошибках и рабочие сценарии доступны на русском языке.

## Компоненты и поток данных

- **React Router** управляет страницами входа, объектов и задач.
- **TanStack Query** загружает данные, повторно запрашивает их после операций и разделяет кэш по пользователю. При выходе или смене пользователя активные запросы отменяются, кэш очищается.
- **Supabase Auth** отвечает за вход по email и паролю и сохранение сессии. Самостоятельная регистрация отключена; учётные записи и роли создаёт администратор.
- **Supabase API и PostgreSQL** обеспечивают чтение с учётом RLS и выполнение изменений через функции базы (RPC).
- **GSAP и CSS** обеспечивают короткие эффекты интерфейса с учётом системной настройки уменьшения движения.

Браузер использует публичный ключ Supabase и сессию текущего пользователя. Роль и автор операции определяются базой по `auth.uid()`, а не принимаются от клиента. Административный ключ не входит в сборку приложения; локальный скрипт наполнения получает его в памяти только для собственного локального стека.

## Модель данных

| Таблица        | Основные поля                                                                                                                         | Назначение                                                                            |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------- |
| `profiles`     | `id`, `full_name`, `role`                                                                                                             | Профиль пользователя; `id` связан с `auth.users.id`, роль — `manager` или `executor`. |
| `projects`     | `id`, `name`, `address`, `created_at`, `updated_at`, `version`, `deleted_at`                                                          | Строительные объекты.                                                                 |
| `tasks`        | `id`, `project_id`, `title`, `description`, `assignee_id`, `author_id`, `status`, `created_at`, `updated_at`, `version`, `deleted_at` | Задачи, связанные с объектом, автором и назначенным исполнителем.                     |
| `task_history` | `id`, `task_id`, `actor_id`, `from_status`, `to_status`, `comment`, `created_at`                                                      | История создания задачи и изменения её статуса.                                       |

Идентификаторы имеют тип UUID, даты — `timestamptz`. `version` — положительное целое число; `deleted_at` задаётся при логическом удалении. Индексы поддерживают выборку действующих задач по объекту и исполнителю, а также истории по задаче и времени. Списки считываются страницами со стабильной сортировкой, чтобы не ограничиваться размером одной страницы API.

Допустимые статусы: `new`, `in_progress`, `in_review`, `accepted`, `rework`. Назначенный исполнитель переводит новую или возвращённую задачу в работу, а выполненную — на проверку. Постановщик принимает задачу на проверке или возвращает её на доработку с непустым комментарием. Остальные переходы запрещены.

## Доступ и изменения

RLS включён на всех четырёх таблицах. Неавторизованные запросы не получают данные. Постановщик видит действующие объекты и задачи компании; исполнитель — только свои задачи, их историю и объекты, к которым относятся эти задачи. Справочник имён и ролей доступен участникам компании и не раскрывает email или другие данные Auth.

У пользователей приложения есть только право `SELECT` на таблицы. Создание, изменение и удаление выполняются через следующие RPC:

| Операция          | Аргументы                                                                                 | Результат      |
| ----------------- | ----------------------------------------------------------------------------------------- | -------------- |
| `create_project`  | `p_name`, `p_address`                                                                     | Объект         |
| `update_project`  | `p_id`, `p_name`, `p_address`, `p_expected_version`                                       | Объект         |
| `delete_project`  | `p_id`, `p_expected_version`                                                              | Без результата |
| `create_task`     | `p_project_id`, `p_title`, `p_description`, `p_assignee_id`                               | Задача         |
| `update_task`     | `p_id`, `p_project_id`, `p_title`, `p_description`, `p_assignee_id`, `p_expected_version` | Задача         |
| `delete_task`     | `p_id`, `p_expected_version`                                                              | Без результата |
| `transition_task` | `p_id`, `p_to_status`, `p_comment`, `p_expected_version`                                  | Задача         |

Каждая операция проверяет сессию, роль и права на соответствующую запись. В операциях изменения и удаления ожидаемая версия обязательна. У `transition_task` аргумент версии имеет SQL-значение по умолчанию `null`, но база отклоняет вызов без фактической версии. Комментарий необязателен, кроме возврата на доработку.

Функции `SECURITY DEFINER` используют пустой `search_path` и явно указанные схемы. Их права вызова ограничены; внутренние помощники размещены в схеме `private`, которая не экспортируется через API. Пользователь не может изменить свою роль через таблицу профилей или метаданные Auth.

## Целостность и конкурентные изменения

Блокировки строк и проверка `version` не позволяют двум запросам незаметно перезаписать друг друга. При устаревшей версии операция возвращает HTTP 409, а интерфейс предлагает обновить карточку. Для таких конфликтов используется код `PT409`: он не запускает повторные попытки, предназначенные для ошибок сериализации PostgreSQL. Переход статуса не может одновременно изменить исполнителя или содержимое задачи.

Триггеры повторно проверяют допустимость изменений задачи и создают запись истории в той же транзакции. Автор, время и исходный статус определяются базой. Клиент не может добавлять, редактировать или удалять записи журнала; дополнительный триггер защищает уже созданную историю. Эти ограничения не заменяют доверие к владельцу базы и администраторам инфраструктуры.

Удаление логическое: задача скрывается из рабочих списков, а её история остаётся в базе. Удаление объекта в одной транзакции скрывает также его задачи. Восстановление удалённых записей через интерфейс не предусмотрено.

## Развёртывание и проверка

[Демонстрационная версия](https://objects-tasks-crm-lilac.vercel.app) размещена на Vercel и использует отдельный проект Supabase на бесплатном тарифе в регионе `eu-central-1`. Все миграции применены; создан демонстрационный набор из трёх объектов, семи задач и четырёх пользователей. Регистрация и анонимный вход отключены, вход по email и паролю включён. Сборка Vercel использует Node.js 22.x и получает только URL Supabase и публичный ключ.

Для локальной работы используются отдельный Docker-стек Supabase и собственные демонстрационные учётные записи. Локальная и облачная базы, пользователи и пароли независимы. Миграции, локальная конфигурация и скрипты наполнения находятся в репозитории; доступы к облачной демонстрации передаются отдельно.

Проверки разделены на unit-тесты клиентских правил, SQL-тесты ограничений базы, запросы к реальному локальному API и браузерные сценарии. GitHub Actions выполняет их на Linux. Команды запуска и результаты локальной проверки приведены в [README](../README.md#проверки).
