# Объекты и задачи

Мини-CRM для строительной компании. Постановщики управляют объектами и задачами; исполнители видят свои задачи, выполняют их и передают на проверку. Все экраны и сообщения — на русском.

**Стек:** React 19, TypeScript, Vite, React Router, TanStack Query, Supabase Auth + PostgreSQL. Отдельного прикладного сервера нет: небольшой клиент обращается к защищённой базе.

## Локальный запуск

Требуются **Node.js 22.12+**, npm и работающий Docker (Docker Desktop на macOS или Docker Engine на Linux). Supabase CLI устанавливается как зависимость проекта. Облачный аккаунт для локального запуска не нужен.

```bash
nvm use
npm ci
npm run setup:local
npm run dev
```

Откройте **http://127.0.0.1:5173**. Первый запуск Supabase скачивает Docker-образы и может занять несколько минут. Выделите Docker достаточно памяти и диска. Проект использует отдельные контейнеры и порты: API `55421`, PostgreSQL `55422`.

`setup:local` запускает Supabase, применяет миграции при первом запуске, создаёт `.env.local` только с публичным ключом и наполняет пустую базу. Повторный запуск сохраняет существующие объекты и пароли. Если наполнение прервалось посередине, выполните локальный сброс и `npm run seed`, чтобы получить полный демонстрационный набор. Если вы добавили миграцию в уже запущенный локальный стек, примените её через `npx supabase migration up` или выполните полный локальный сброс, описанный ниже.

### Остановка и сброс

Остановить интерфейс: `Ctrl+C` в его терминале. Остановить Supabase с сохранением данных: `npm run db:stop`.

**Полностью удалить данные только этой локальной CRM и заново наполнить демонстрационными:**

```bash
npm run db:reset
npm run seed
```

Этот сброс разрушителен для локальных объектов и задач. Скрипт наполнения получает административный ключ запущенного локального стека в памяти; не записывает его в `.env.local` или исходники и не принимает удалённый адрес.

## Экраны и работа

- Вход по email и паролю; открытой регистрации нет.
- Объекты: список, поиск, карточка с задачами. Постановщик создаёт, редактирует и удаляет объекты.
- Задача: название, описание, объект, исполнитель, автор, дата создания, статус и история. Постановщик создаёт, редактирует, назначает и удаляет задачи.
- «Мои задачи»: исполнителю доступны только назначенные ему задачи; поиск и фильтр статуса.
- В карточке видны только действия, доступные текущей роли и статусу. При возврате на доработку нужен непустой комментарий.
- После сохранения данные перечитываются; устаревшее изменение отклоняется с предложением обновить карточку. Перезагрузка страницы сохраняет вход и данные.

В интерфейсе добавлены объёмный макет стройки на экране входа, лёгкий наклон карточек и короткие анимации окон и подтверждений. Эффекты используют GSAP и CSS, не запускают бесконечные циклы и отключаются при системной настройке уменьшения движения. Работа с клавиатурой и мобильные экраны сохранены.

## Как защищены данные

Проверки интерфейса служат удобству. Безопасность обеспечивается PostgreSQL и действует при прямом обращении к Supabase API.

1. **RLS (правила доступа к строкам)** включены на `profiles`, `projects`, `tasks`, `task_history`. Анонимный запрос не читает данные. Исполнитель читает только свои задачи, их историю и объекты, где есть его задачи. Вложенные API-запросы подчиняются тем же правилам.
2. У обычных пользователей нет прямого `INSERT`, `UPDATE`, `DELETE` к таблицам. Изменения выполняются через небольшие **RPC** — заранее определённые операции в базе. Каждая проверяет личность из подписанной сессии, роль и права на запись. Клиент не передаёт роль или автора.
3. Все переходы проверяются в базе. Дополнительный триггер защищает задачу, если в будущем права на таблицу будут ошибочно расширены. Нельзя перепрыгнуть статус, принять собственную исполнительскую задачу или вернуть задачу без комментария.
4. Историю создаёт триггер в той же транзакции, что меняет статус. Кто и когда действовал, определяет база. Для API журнал недоступен на запись, изменение и удаление; отдельный триггер запрещает изменение существующих записей журнала.
5. Блокировка строки и номер версии защищают от одновременного принятия/возврата и сохранения устаревшей формы. Либо применяются и статус, и запись истории, либо не применяется ничего.
6. `SECURITY DEFINER` функции имеют пустой `search_path`, явные схемы и ограниченные права вызова. Внутренние помощники находятся в неэкспортируемой схеме `private`.
7. Роли хранятся в защищённой таблице, а не в пользовательских метаданных. Изменить свой профиль/роль через API нельзя. Пользователя и его роль создаёт только администратор.
8. Регистрация отключена на уровне локального Auth, включая прямой запрос `signUp`. Во фронтенде используется только публичный `anon`/publishable ключ; административный `service_role` нельзя публиковать. Владельцы базы и администраторы Supabase остаются доверенными лицами.

## Переходы статусов

| Из           | В            | Кто                         |
| ------------ | ------------ | --------------------------- |
| Создание     | Новая        | Постановщик                 |
| Новая        | В работе     | Назначенный исполнитель     |
| В работе     | На проверке  | Назначенный исполнитель     |
| На проверке  | Принята      | Постановщик                 |
| На проверке  | На доработке | Постановщик, с комментарием |
| На доработке | В работе     | Назначенный исполнитель     |

Все остальные переходы запрещены. Статус нельзя изменить в форме редактирования.

## Проверки

```bash
npm run check                 # TypeScript, unit-тесты, production build
npm run test:db               # SQL-тесты неизменяемой истории и прав
npm run test:security         # реальные запросы к локальному Supabase API
npx playwright install chromium
npm run test:e2e              # реальные браузерные сценарии
```

Перед интеграционными проверками выполните `npm run setup:local`. Тесты безопасности не используют административный ключ и специально отказываются работать с удалённым адресом. Они проверяют роли, видимость чужих данных, все сочетания переходов, подделку истории, обход RPC, смену исполнителя, гонки, пустые комментарии и отключённую регистрацию. Тестовые записи удаляются логически после прогона; при необходимости чистой демонстрации сбросьте локальную базу.

GitHub Actions (`.github/workflows/ci.yml`) запускает проверки на Linux при push и pull request: чистый `npm ci`, сборку, локальный Supabase, SQL-, API- и браузерные тесты. Результат каждого удалённого прогона доступен во вкладке Actions; локальные результаты ниже не заменяют его.

На 6 ноября 2026 года локально прошли: 22 unit-теста, 22 API-теста (включая 75 сочетаний переходов и ролей), 16 SQL-проверок и 5 браузерных сценариев. Проверены ошибки входа, CRUD, доработка и приёмка, сохранение после перезагрузки, смена пользователя, чужие прямые ссылки, устаревшие изменения и мобильная ширина 390 px. Аудит зависимостей: 0 известных уязвимостей на момент проверки. Отдельно пройдены чистый `npm ci`, TypeScript, все 22 unit-теста и production-сборка в Linux-контейнере Node.js 22 без локальных настроек и учётных данных.

```text
src/
  components/           общие элементы интерфейса и навигация

```

## Подключение облачного Supabase и публикация

Публичная работающая версия пока не развёрнута. Репозиторий содержит приложение, миграции и конфигурацию для развёртывания. Для публикации сайта:

1. Создайте отдельный проект Supabase и отключите **Allow new users to sign up** в настройках Auth. Локальный `config.toml` сам по себе не меняет облачные настройки. Отключите также анонимный вход.
2. Выполните `npx supabase login`, `npx supabase link --project-ref YOUR_PROJECT_REF`, затем `npx supabase db push`. Проверяйте выбранный проект перед применением миграций.
3. Создайте пользователей вручную через Supabase Auth и подтвердите email. В SQL Editor добавьте профиль для каждого созданного UUID:

   ```sql
   insert into public.profiles (id, full_name, role)
   values ('UUID_ИЗ_AUTH', 'Имя пользователя', 'manager');
   -- Для исполнителя role = 'executor'.
   ```

4. Скопируйте `.env.example` в `.env.local`, укажите URL проекта и только публичный ключ. Для production задайте эти же `VITE_*` в хостинге. Никогда не ставьте `service_role` или `sb_secret_*` в `VITE_*`.
5. Добавьте адрес сайта в настройки Auth Site URL/Redirect URLs. Запустите `npm run build`; публикуется каталог `dist`. `vercel.json` содержит маршрутизацию SPA для обновления внутренних страниц.
6. Войдите постановщиком и создайте демонстрационные объекты/задачи. Локальный скрипт `seed` намеренно не наполняет облачную базу.
7. После публикации отдельно проверьте вход каждого пользователя, создание/изменение, полный цикл статусов, сохранение после перезагрузки и прямые запретные API-запросы. Локальный успешный прогон не подтверждает настройки облачного проекта.

Не добавляйте `.env.local`, `.local/`, реальные пароли, токены Supabase CLI или административные ключи в репозиторий.
